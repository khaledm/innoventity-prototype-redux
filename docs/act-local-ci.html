Testing GitHub Actions locally with act

TL;DR — act runs GitHub Actions job steps inside Docker containers on your local machine. Run from the repo root: act -W '.github/workflows/deploy-frontend.yml' -j test. Two things are required in this repo: add if: ${{ !env.ACT }} to every upload-artifact@v7 step (the v4 protobuf protocol has a mime_type field act's server doesn't understand), and avoid running deploy/validate jobs that require live Azure by using -j <jobname> to target only build/test. Config lives in .actrc (platform image pin + secret file path) and .secrets (never commit — gitignored).

What act is and why it helps

nektos/act reads your .github/workflows/*.yml files and runs each job step inside a Docker container that mirrors the GitHub-hosted runner environment. You get fast, local CI feedback without pushing commits to trigger the real pipeline.

Why not just push and let GitHub run it? speed & cost

Each push to Main triggers the full 6-job deploy pipeline: preflight → build-test → migrate → deploy → pester-health → slot-swap. A full green run takes 8–12 minutes. A push just to verify a YAML syntax fix or a new workflow step is wasteful — in both wait time and GitHub Actions minutes.

act -W '.github/workflows/deploy-frontend.yml' -j test --dryrun resolves which steps would run in under 5 seconds without spinning up a single container.

What act can and cannot do scope

Works fully locally: shell steps, tool installs (dotnet, node, etc.), build & compile steps, unit tests, if: condition evaluation, job outputs, secrets from .secrets, environment variables.

Works locally with live credentials: Azure CLI login, Terraform state reads from Azure Blob Storage, DB migrations via dotnet ef against Azure SQL, App Service zip-deploy. These require all ARM_* and DB_CONNECTION_STRING secrets in .secrets.

Cannot be meaningfully tested locally: Azure Static Web Apps deploy (Azure/static-web-apps-deploy@v1 calls SWA's own API), slot swaps, pester health checks against a live deployed URL, and E2E Playwright tests (need the full live stack).

Setup

Three things needed: Docker Desktop running, act installed, and two config files placed in the repo root.

1 · Prerequisites once per machine

Docker Desktop must be running before any act command. Verify with docker ps. Then install act:

# Windows — winget (recommended)
winget install nektos.act

# or Chocolatey
choco install act-cli

# Verify installation
act --version

Create the artifact server directory once. act panics on Windows if the path in .actrc doesn't exist at startup:

New-Item -ItemType Directory -Force -Path C:\tmp\act-artifacts
2 · .actrc — persistent defaults .actrc (gitignored)

Place .actrc in the repo root. act reads it on every invocation, so you never need to repeat these flags on the command line:

# .actrc
--platform ubuntu-latest=catthehacker/ubuntu:act-22.04
--secret-file .secrets
--artifact-server-path C:\tmp\act-artifacts

Why catthehacker/ubuntu:act-22.04? act's default micro image is missing dotnet, curl, zip, and other tools used in every workflow in this repo. The "medium" image (~500 MB, pulled once then cached) includes all of these. The first pull takes ~2 minutes; subsequent runs start in seconds.

.actrc is gitignored in this repo (see the act section in .gitignore). Each developer keeps their own local copy — the C:\tmp\act-artifacts path is Windows-specific.

3 · .secrets — local secret values .secrets (gitignored)

Create .secrets in the repo root. Format is KEY=value, one per line — identical to a .env file. It is gitignored and must never be committed.

# .secrets — NEVER commit this file
DB_CONNECTION_STRING=Server=tcp:innoventity-dev-sql.database.windows.net,1433;Initial Catalog=Innoventity;...
ARM_CLIENT_ID=<value>
ARM_CLIENT_SECRET=<value>
ARM_SUBSCRIPTION_ID=<value>
ARM_TENANT_ID=<value>

Get DB_CONNECTION_STRING from Terraform state:

cd infrastructure/environments/dev/data
terraform output -raw connection_string

Jobs that don't touch Azure (build, test, quality-nightly) work fine with an empty .secrets file. Only migrate and the deploy jobs need live values.

Running workflows locally

Always run act from the repo root. It looks for .github/workflows/ relative to the current working directory. Running from a subdirectory (e.g. src/Innoventity.API) causes an immediate path error (see Known Issues).

⚠
If you've been working in a terminal pointed at src/Innoventity.API or src/Innoventity.Client, always cd back to the repo root before invoking act: cd C:\Users\mahmu\source\repos\innoventity-prototype-redux
# Run the test job (act automatically runs build first, because test needs: build)
act -W '.github/workflows/deploy-frontend.yml' -j test

# Run only the build job
act -W '.github/workflows/deploy-frontend.yml' -j build
# Apply EF Core migrations to Azure SQL dev database
# Requires DB_CONNECTION_STRING in .secrets
act -W '.github/workflows/deploy.yml' -j migrate
# See which steps would execute — no Docker containers started, no network calls
act -W '.github/workflows/deploy-frontend.yml' -j test --dryrun

# Dry run the full deploy pipeline
act -W '.github/workflows/deploy.yml' --dryrun
# Run mutation tests (Stryker) — fully self-contained, no Azure needed
act -W '.github/workflows/quality-nightly.yml'
# Run the full deploy.yml chain — touches real Azure infrastructure
# Requires all ARM_* secrets, live App Service, and DB provisioned
act -W '.github/workflows/deploy.yml'

# Tip: use workflow_dispatch event to avoid triggering deploy-production
# (which has: if: github.event_name == 'push')
act workflow_dispatch -W '.github/workflows/deploy-frontend.yml'
★
act always resolves needs: dependency chains. Running -j test automatically runs build first because test: needs: build. To skip dependencies, add --no-dep-jobs (act v0.2.52+).

Known issues and fixes

Each of these was encountered while testing this repo with act and is documented here for reference.

upload-artifact@v7 — mime_type protobuf error deploy-frontend.yml · deploy.yml

actions/upload-artifact@v7 uses the GitHub Artifact v4 API, which sends protobuf-encoded payloads. act's artifact server doesn't recognise the mime_type field in the schema — it responds with a decode error, the action retries 5 times, then fails the job.

Error output:

level=error msg="Error decode request body: proto: (line 1:142): unknown field \"mime_type\""
Attempt 1 of 5 failed with error: Unexpected end of JSON input. Retrying in 3000 ms...
...
::error::Failed to CreateArtifact: Failed to make request after 5 attempts

Fix: add if: ${{ !env.ACT }} to every upload-artifact step. act automatically sets the ACT environment variable to true, so the step is skipped locally and runs normally in GitHub Actions CI.

# Steps with no existing if: condition
- name: Upload build artifact
  if: ${{ !env.ACT }}
  uses: actions/upload-artifact@v7
  with:
    name: frontend-build
    path: ...

# Steps that already have if: always()
- name: Upload test results
  if: ${{ always() && !env.ACT }}
  uses: actions/upload-artifact@v7
  with:
    name: test-results-${{ github.run_id }}
    ...

Apply the same guard to any download-artifact step in jobs that depend on the artifact — or skip those jobs entirely (see next issue).

Deploy jobs run unexpectedly — act defaults to push event deploy-frontend.yml

When you run act -W 'deploy-frontend.yml' without specifying an event, act defaults to the push event with github.ref = refs/heads/Main. Jobs guarded by if: github.event_name == 'push' && github.ref == 'refs/heads/Main' then evaluate to true and try to run — including a download-artifact step that panics because nothing was uploaded.

Option A — target only the jobs you need (recommended for daily use):

act -W '.github/workflows/deploy-frontend.yml' -j test

Option B — use the workflow_dispatch event, which doesn't match the push condition:

act workflow_dispatch -W '.github/workflows/deploy-frontend.yml'

Option C — add !env.ACT to the deploy job's if condition (permanent guard that works regardless of how act is invoked):

deploy-production:
  if: ${{ !env.ACT && github.event_name == 'push' && github.ref == 'refs/heads/Main' }}
Windows path panic — artifact server directory must exist .actrc

act's artifact server opens the --artifact-server-path directory at startup. On Windows, if C:\tmp\act-artifacts doesn't exist, the Go server goroutine panics immediately:

panic: open C:\tmp\act-artifacts\1: The system cannot find the path specified.
goroutine 6946 [running]:
net/http.(*conn).serve.func1() ...

Create the directory once and it persists across all future runs:

New-Item -ItemType Directory -Force -Path C:\tmp\act-artifacts
Wrong working directory — act run from a subdirectory repo root

Running act from inside src/Innoventity.API (e.g. after a dotnet ef session) causes:

Error: GetFileAttributesEx C:\...\src\Innoventity.API\.github\workflows:
The system cannot find the path specified.

act looks for .github/workflows/ relative to the current directory. Always cd to the repo root first:

cd C:\Users\mahmu\source\repos\innoventity-prototype-redux
act -W '.github/workflows/deploy-frontend.yml' -j test

Gotchas worth knowing

  • First image pull is slow. catthehacker/ubuntu:act-22.04 is ~500 MB and downloaded once. Docker caches it; subsequent runs start the container in 2–4 seconds.
  • ACT=true is always set inside act containers. Any step that should behave differently locally can test if: ${{ !env.ACT }}. This is the standard act compatibility pattern and is recognised by the community.
  • Non-terminating git clone warnings are harmless. act clones marketplace actions into its local cache (~/.cache/act/). The message "Non-terminating error while running 'git clone': some refs were not updated" appears on shallow-clone ref mismatches — the cached action still loads and runs correctly.
  • Node version discrepancy in output. The act image has Node 24.x pre-installed, but setup-node@v6 with node-version: 20.x resolves to v20 from the tool cache. Both coexist; the right one is activated. This is expected.
  • Angular bundle budget warning is not a failure. The build emits "innovation-detail.component.scss exceeded maximum budget (5.01 kB vs 4 kB limit)". This is configured as a warning in angular.json, not an error — the job exits 0. Address it by raising the budget or trimming the SCSS.
  • .actrc and .secrets are gitignored. If you clone to a new machine, both files must be recreated manually. The canonical content for this repo is in the Setup section above.
  • act vs real CI parity isn't 100%. act doesn't emulate GitHub-specific context variables like GITHUB_TOKEN permissions, Environments with required reviewers, or the GitHub Actions cache service (actions/cache). For parity testing of those features, a real push is still required.

FAQ

How do I run a job without running its dependencies?
Use --no-dep-jobs (act v0.2.52+): 
act -W '.github/workflows/deploy.yml' -j migrate --no-dep-jobs
Without this flag, act always runs needs: dependency chains first.
Can I pass a secret inline instead of using .secrets?
Yes — the -s flag takes precedence over .secrets: 
act -j migrate -s DB_CONNECTION_STRING="Server=tcp:..."
Avoid this in shared terminals where shell history may capture the value.
The migrate job says "No migrations were applied. Database is already up to date." — is that a problem?
No. EF Core queries __EFMigrationsHistory, finds all 9 migration rows already present (from the April 2026 deployment), and exits 0 with that message. The database schema is current. This is the expected idempotent behaviour of dotnet ef database update.
Why did the old migrate job keep failing even after fixing dotnet-ef version?
The original 9-step migrate job included schema drift detection using sqlcmd. On Ubuntu 24.04, mssql-tools18 emits informational messages (e.g. "Changed database context to 'Innoventity'.") to stdout, not stderr. After | tr -d '[:space:]', the captured variable was never empty — causing every validation check to report a false positive. The fix was to remove all three custom layers (Terraform, sqlcmd, drift detection) and let EF Core handle everything natively.
How do I update act?
winget upgrade nektos.act    # or: choco upgrade act-cli
act --version
The artifact server's v4 support improves in each release, which may eventually remove the need for !env.ACT guards on upload-artifact steps.
Why is .actrc gitignored?
.actrc contains --artifact-server-path C:\tmp\act-artifacts — a Windows-specific path. Team members on macOS or Linux would use a different path (e.g. /tmp/act-artifacts). Gitignoring it lets each developer maintain their own local config without conflicts.
Can I test the SWA deploy job locally?
Azure/static-web-apps-deploy@v1 calls the SWA service API directly using AZURE_STATIC_WEB_APPS_API_TOKEN. Technically the token can be placed in .secrets and the step will execute — but it will attempt a real deployment to your dev SWA resource. There is no SWA emulator. Treat the deploy and validate jobs as CI-only; use -j test for local iteration.
